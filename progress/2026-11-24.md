### 2. Recipe database model

I created the recipe schema in `backend/models/Recipe.js` so recipe data is stored consistently in MongoDB.

The model includes:

| Field | Details |
| ----- | ------- |
| `title` | Required, trimmed, maximum 100 characters |
| `description` | Required, trimmed, maximum 1000 characters |
| `ingredients` | Required array of strings; must contain at least one non-empty ingredient |
| `steps` | Required array of strings; must contain at least one non-empty cooking step |
| `image` | Optional string, defaults to `null` |
| `servings` | Number, defaults to `2`, minimum value `1` |
| `tags` | Array of strings, defaults to an empty array |
| Timestamps | `createdAt` and `updatedAt` added automatically by Mongoose |

Validation messages are written for required fields and for empty ingredient/step arrays, so API errors are easier to understand.

### 3. Recipe APIs — create, get all, get by ID, update, and delete

I implemented the full CRUD functionality in `backend/controllers/recipeController.js` and wired the routes in `backend/routes/recipeRoutes.js`.

#### Create recipe — `POST /api/recipes`

- Reads `title`, `description`, `ingredients`, `steps`, `servings`, and `tags` from the request body.
- Checks that `title`, `description`, `ingredients`, and `steps` are provided.
- Returns `400` with `"All required fields must be provided"` if any required field is missing.
- Creates the document with `Recipe.create()`.
- Returns `201` with `success: true`, a success message, and the created recipe.

#### Get all recipes — `GET /api/recipes`

- Fetches every recipe from MongoDB with `Recipe.find()`.
- Sorts results by `createdAt` in descending order, so the newest recipes come first.
- Returns `200` with `success: true`, the total `count`, and the `recipes` array.

#### Get recipe by ID — `GET /api/recipes/:id`

- Finds one recipe using `Recipe.findById(req.params.id)`.
- Returns `404` with `"Recipe not found"` when the ID is valid but no recipe exists.
- Returns `400` with `"Invalid recipe ID"` when the ID is not a valid MongoDB ObjectId (`CastError`).
- Returns `200` with `success: true` and the matching recipe on success.

#### Update recipe — `PUT /api/recipes/:id`

- Updates a recipe with `Recipe.findByIdAndUpdate()`.
- Uses `{ new: true }` so the response contains the updated document.
- Uses `{ runValidators: true }` so schema rules are checked during updates.
- Supports partial updates, for example changing only `servings` or `tags`.
- Returns `404` if the recipe does not exist and `400` for an invalid ID.
- Returns `200` with a success message and the updated recipe.

#### Delete recipe — `DELETE /api/recipes/:id`

- Deletes a recipe with `Recipe.findByIdAndDelete(req.params.id)`.
- Returns `404` if the recipe does not exist and `400` for an invalid ID.
- Returns `200` with `success: true` and `"Recipe deleted successfully"`.

All controller errors are passed to the Express error handler using `next(error)`, so unexpected failures are handled in one place.

### 7. User signup and login

I completed user accounts and JWT authentication for the backend.

- Created `backend/models/User.js` with a required name, a unique lowercase email, and a password field marked `select: false` so it is never returned by normal queries.
- Created `backend/controllers/authController.js`:
  - `signup` hashes the password with `bcryptjs` using 12 salt rounds, creates the user, and returns a token plus a public user object without the password.
  - Duplicate emails return `409`; the unique index also protects against races.
  - `login` loads the user with `select("+password")`, compares the password with bcrypt, and returns the same token/user shape.
  - Failed login uses one generic message, `"Invalid email or password"`, so the API does not reveal whether an email exists.
  - `getMe` returns the user attached to the current token.
- Created `backend/middleware/auth.js`:
  - Generates HS256 JWTs using `JWT_SECRET` and `JWT_EXPIRES_IN`.
  - Verifies tokens with `algorithms: ["HS256"]` to block algorithm confusion.
  - The `protect` middleware requires an `Authorization: Bearer <token>` header, verifies the token, reloads the user from MongoDB, and attaches it to `req.user`.
- Created `backend/routes/authRoutes.js` with `POST /api/auth/signup`, `POST /api/auth/login`, and `GET /api/auth/me`.
- Added validation rules requiring a valid email, a 8–100 character password with at least one letter and one number, and a name up to 50 characters.
- Made recipe writes (create, bulk create, update, delete) protected while recipe reads remain public.
- Added a `createdBy` reference to the `Recipe` model and set it automatically from the logged-in user.

### 8. Bulk recipe creation

I added a bulk endpoint so many recipes can be inserted in one request.

- Created `POST /api/recipes/bulk`, registered before `/:id` so `"bulk"` is not treated as a MongoDB ObjectId.
- The endpoint accepts a `recipes` array containing between 1 and 100 items.
- Every item is validated with the same field rules as a single recipe.
- I used `Recipe.insertMany(recipes, { ordered: false })` for efficient insertion.
- The response returns `success`, a created count, and all inserted documents.
- I gave bulk requests their own rate limit of 5 requests per hour.
- I copied only whitelisted fields into each document and attached `createdBy` automatically, preventing mass assignment.

### 9. Cyber attack prevention

I added layered protection against common web attacks.

- Installed `helmet`, `express-rate-limit`, `express-mongo-sanitize`, `hpp`, `xss`, `express-validator`, `bcryptjs`, and `jsonwebtoken`.
- Added three rate limits: 100 API requests per 15 minutes, 10 auth attempts per 15 minutes, and 5 bulk requests per hour.
- Restricted CORS to the comma-separated origins in `CLIENT_ORIGIN`, defaulting to `http://localhost:5173`, and return `403` for blocked origins.
- Enabled `helmet()` security headers and disabled `x-powered-by`.
- Sanitized MongoDB operator keys (`$ne`, `$where`, etc.) into `_ne` / `_where` before data reaches Mongoose.
- Added `hpp()` with a whitelist for `ingredients`, `steps`, `tags`, and `recipes` so legitimate arrays survive while duplicate-parameter pollution is collapsed.
- Added XSS escaping for user-supplied strings with `xss()`, while leaving password values untouched for bcrypt.
- Limited JSON bodies to 1 MB and return `413` for oversized requests.
- Added `express-validator` checks for all auth and recipe fields plus MongoDB ObjectId checks on `:id` routes.
- Replaced raw `req.body` writes with an explicit field whitelist, so fields such as `createdBy` or internal keys cannot be injected.
- Centralized error handling now logs details server-side, returns a generic `500` message in production, and handles malformed JSON, validation errors, duplicate keys, and invalid IDs.
- Created `backend/.env.example` with placeholder values and generated a real local `JWT_SECRET` in the untracked `backend/.env`.
- I encountered an Express 5 incompatibility: `express-mongo-sanitize` middleware tried to assign to the read-only `req.query`. I fixed it by calling its `sanitize()` function directly on `req.body` and `req.params` in a custom middleware.
- Updated the root `README.md` with all of the new environment variables, auth flow, endpoints, security measures, and data models.
